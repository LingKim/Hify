# Provider 管理方案设计

## 1. 背景

Hify 需要支持多 LLM 供应商管理，并基于 LiteLLM 作为执行层统一对接不同厂商。

当前一期目标不是构建一个复杂的调度平台，而是先完成：

- 提供商配置管理
- 模型配置管理
- 鉴权信息安全存储
- 后台单页面管理
- 后续向多模型、多实例、健康检查、路由策略扩展

## 2. 一期范围

一期范围：

- 后端维护 Provider 实例、密钥、模型、健康状态四类核心数据
- 前端只做一个“模型提供商管理”页面
- 页面可以增删改查 Provider
- 一个 Provider 页面项可同时维护基础信息、鉴权信息和模型列表
- 模型不做自动发现，全部手工维护

一期不做：

- 供应商模型自动同步
- 路由编排
- 流量分配
- 多 Provider fallback
- 外部密钥管理器集成
- 模型级健康状态

## 3. 核心设计原则

### 3.1 前端单页，后端分层

前端只维护一个页面，不拆成“提供商管理页”和“模型管理页”。

但后端仍然保留分层领域模型：

- `provider_instance`
- `provider_auth_secret`
- `provider_model`
- `provider_health_status`

原因：

- 前端简化不应该牺牲后端扩展性
- 后面同一 Provider 挂多个模型时，不需要重做数据库
- 健康状态和鉴权天然属于实例级，不适合塞进一条扁平记录

### 3.2 聚合接口优先

前端虽然是单页面，但不代表后端资源必须扁平化。

一期接口采用“聚合读写”的方式：

- 列表页读 Provider 摘要
- 详情页读 Provider 聚合详情
- 创建和更新时一次性提交 Provider、Auth、Models

这样既满足前端易用性，也保留了后端内部可演进性。

### 3.3 模型是平台配置，不是供应商事实

由于本期不做自动发现，模型表中的记录表示：

“Hify 内部允许管理员维护的模型配置”

而不是：

“供应商平台自动同步到的客观事实模型列表”

因此模型表字段需要更强调：

- 展示名
- 是否默认
- 是否启用
- 能力标签
- 参数边界

## 4. 鉴权存储设计

一期采用数据库密文存储。

设计原则：

- 数据库不存明文 secret
- 数据库存加密后的 `secret_ciphertext`
- 接口返回只回 `secretMasked`
- 写入时支持统一结构化载荷

统一载荷结构包括：

- `secret_value`
- `headers`
- `query_params`
- `metadata`

这样可以兼容：

- OpenAI Bearer Key
- Anthropic Header Key
- Gemini API Key
- Ollama 无鉴权或自定义 Header
- OpenAI compatible 的扩展 Header 或 Query 参数

## 5. 模块边界

后端模块职责：

- 持久化 Provider 配置
- 校验单个 Provider 下模型唯一性与默认模型唯一性
- 加解密鉴权信息
- 输出前端单页所需的聚合数据

LiteLLM 职责：

- 作为模型调用执行层
- 适配不同提供商协议

当前 Provider 管理模块并不直接承载 LiteLLM 的所有运行时能力，而是为其提供配置来源。
