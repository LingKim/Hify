# Hify MVP 开发计划

## 1. 目标

本文档基于根目录 `CLAUDE.md` 中定义的 MVP 功能清单，结合当前仓库实际进展，整理后续开发计划。

本文档解决三个问题：

- MVP 清单里的每一项，当前做到什么程度
- 后续应该按什么顺序开发，而不是按功能名机械平铺
- 每一阶段完成后，平台能形成什么可验证能力

## 2. 当前状态判断

结合当前代码和设计文档，项目现状可以归纳为：

- 已有前后端基础骨架、统一请求层、主题系统、测试基础设施
- `模型管理` 已经进入一期可用状态，完成了 Provider 聚合 CRUD、密钥加密、前端管理页、连接测试和调用测试
- `agent` 已经完成配置 CRUD、模型绑定、工具绑定、知识库绑定和前端管理页，Workflow Agent 仍只能保存草稿
- `conversation` 已经完成会话 CRUD、消息历史、SSE 流式输出、LiteLLM 调用和 Web 对话页
- `knowledge` 已经完成知识库 CRUD、文档上传、切片、Embedding、PGVector 检索测试和 Conversation RAG 注入的基础闭环
- `tool` 已经完成工具 CRUD、OpenAPI 预览、HTTP 测试执行和 Conversation 单轮工具调用闭环
- `auth / user-management` 已经完成账密登录、JWT、前端登录态闭环和内部用户管理
- `可观测性` 已有基础会话日志、工具执行日志和检索日志，但还缺少统一排查视图
- `发布与集成`、`工作流引擎` 和 `Docker Compose` 交付闭环尚未完成

这意味着后续开发不能平均铺开，而要围绕主链路推进：

`主链路校准 -> 发布集成 -> 可观测性 -> 工作流引擎 -> 部署收口`

## 3. 规划原则

### 3.1 按 MVP 清单管理，按依赖顺序开发

根 `CLAUDE.md` 里的 MVP 清单是产品范围，不是编码顺序。

后续执行时，文档仍按 MVP 清单逐项管理，但实际开发顺序以依赖关系为准。

### 3.2 先打通单 Agent 主链路，再扩展复杂编排

Hify 的核心不是“先做很多配置页”，而是先让用户完成这条链路：

`创建 Agent -> 绑定模型 -> 发起对话 -> 得到稳定回复`

只有这条主链路跑通后，知识库、工具、发布、工作流才有真实挂载点。

### 3.3 Chatbot 模式不单独做一套系统

MVP 中提到 `Agent 模式 + Chatbot 模式`，但落地时不建议做两套并行架构。

更合理的做法是：

- `Agent 模式` 作为完整能力形态
- `Chatbot 模式` 作为受限版 Agent 模板

也就是：

- 固定单模型
- 默认不开工具
- 可选不开知识库
- 仍复用同一套对话与发布链路

这样可以减少后端和前端重复实现。

### 3.4 工作流引擎放到 MVP 后半程

工作流引擎是平台差异化能力，但也是当前清单里实现成本最高、跨模块依赖最多的一项。

如果在 Agent 主链路没有跑通之前就进入工作流开发，后续大概率会反复返工。

因此工作流引擎仍属于 MVP 范围，但排在后半程开发。

## 4. 建议实际开发顺序

建议按下面的阶段推进：

| 阶段 | 对应 MVP 能力 | 目标 |
|---|---|---|
| P0 | 模型管理 | 把当前 Provider 管理模块补到稳定可复用 |
| P1 | 应用编排 | 完成 Agent 配置模块，形成“可保存的 AI 应用” |
| P2 | 应用编排 / 发布与集成 | 打通对话运行时，支持 Web 对话和 SSE |
| P3 | 知识库 / RAG | 让 Agent 能基于私有知识回答 |
| P4 | 工具集成 | 让 Agent 能调用外部 API 做动作 |
| P5 | 发布与集成 | 提供正式应用入口和外部调用接口 |
| P6 | 可观测性 | 形成运行日志、错误追踪和基础分析能力 |
| P7 | 团队管理 | 接入登录、角色和基础权限 |
| P8 | 工作流引擎 | 引入节点编排能力，补齐复杂场景 |
| P9 | 部署 | 完成 Docker Compose 一键交付闭环 |

下面各节仍按根 `CLAUDE.md` 的 MVP 功能清单顺序展开。

## 5. 分项开发计划

### 5.1 应用编排

对应清单：

- Agent 模式
- Chatbot 模式
- 用配置文件 / 表单替代可视化编辑器

当前状态：

- 后端 `agent` 模块已经具备 ORM、schema、service、router。
- 前端已经具备 Agent 配置页面、domain 五件套、路由和菜单入口。
- Agent 可绑定模型、工具和知识库。
- 对话运行会读取 Agent 配置，Workflow Agent 当前只能保存草稿，不能启用运行。

开发目标：

- 定义 Agent 作为平台核心应用单元
- 支持创建、编辑、删除、查看 Agent
- 支持绑定默认模型
- 支持配置系统提示词、欢迎语、建议提问
- 支持配置基础对话行为，如是否保留上下文、是否允许工具调用、是否启用知识库
- 以 `app type` 或模板方式兼容 Chatbot 模式

本阶段产出：

- Agent 数据模型与关联关系
- Agent CRUD 接口
- Agent 管理页面
- Agent 配置表单
- Agent 详情 / 测试入口

完成标准：

- 管理员可以创建一个 Agent
- Agent 至少能绑定一个模型
- Agent 配置可以被后续对话模块直接消费

建议排期：

- 已完成主体能力；后续仅做发布、运行排查和 Workflow 扩展时的配套增强。

### 5.2 工作流引擎

对应清单：

- LLM 节点
- IF / ELSE 条件分支
- HTTP Request 节点
- 代码执行节点
- Prompt 变量

当前状态：

- 仓库中尚无工作流实体、执行器或前端编排页

开发目标：

- 建立工作流定义模型
- 建立节点执行上下文和变量传递机制
- 支持最小节点集：LLM、条件分支、HTTP 请求、Prompt 变量
- 代码执行节点放在工作流后段实现，避免过早引入沙箱复杂度

本阶段产出：

- Workflow 数据模型
- Workflow 执行引擎
- 最小节点协议
- Workflow 调试 / 运行接口

完成标准：

- 能保存并执行一个最小工作流
- 能在节点间传递上下文和变量
- 能从 Agent 或独立入口触发工作流

建议排期：

- `P8`

说明：

工作流虽然在清单里靠前，但不应先于 Agent 主链路开发。

### 5.3 知识库 / RAG

对应清单：

- 文档上传
- 文本切片
- 向量索引（PGVector）
- 检索测试

当前状态：

- 后端 `knowledge` 模块已经具备 ORM、schema、service、router。
- 已有知识库、文档、切片、检索日志相关迁移。
- 已实现文档上传、文本抽取、切片、Embedding、PGVector 检索测试。
- 前端已有知识库工作台页面。
- Conversation 已能根据 Agent 绑定知识库执行 RAG 检索并注入上下文。

开发目标：

- 支持知识库实体管理
- 支持文档上传、解析、切片、Embedding、入库
- 支持检索测试和命中结果查看
- 支持 Agent 绑定单知识库

本阶段产出：

- `knowledge_bases / knowledge_documents / knowledge_chunks` 等数据结构
- 文档处理任务链路
- 检索接口
- 知识库管理页面
- 检索测试页面或测试弹窗

完成标准：

- 用户可以上传文档并完成索引
- Agent 对话时可基于知识库进行检索增强
- 用户能看到检索是否命中以及命中了什么

建议排期：

- 已完成一期基础闭环；后续进入召回质量、引用展示和排查视图增强。

### 5.4 模型管理

对应清单：

- 多模型接入（OpenAI + Claude + Gemini + Ollama）
- 模型参数配置

当前状态：

- 已完成 Provider 聚合 CRUD
- 已完成密钥加密与基础模型配置
- 已有前端 Provider 管理页和一期设计文档
- 已有连接测试、调用测试和 LiteLLM 运行时配置解析

待继续内容：

- Provider 配置与 Agent 绑定链路联调
- 更完整的错误处理与集成测试

本阶段产出：

- 稳定的 Provider 与 Model 配置来源
- 可被 `agent` 与 `conversation` 复用的模型选择能力
- 健康状态与调用能力校验

完成标准：

- 管理员可以稳定维护 Provider 和模型
- 后续 Agent 配置页可以直接引用模型列表
- 对话运行时可以真实调用已配置模型

建议排期：

- 已完成一期基础能力；后续随发布、运行和观测需求继续增强。

### 5.5 工具集成

对应清单：

- 自定义工具
- OpenAPI 导入
- 用户自行接入 API

当前状态：

- 后端 `tool` 模块已经具备 ORM、schema、service、router。
- 已实现工具 CRUD、OpenAPI 预览、HTTP 测试执行和执行日志。
- 前端已有工具集成页面。
- Agent 配置页可选择真实工具。
- Conversation 已支持单轮工具调用，并通过 SSE 输出工具事件。

开发目标：

- 支持工具基本信息管理
- 支持 OpenAPI 导入生成工具定义
- 支持 HTTP 工具执行
- 支持 Agent 配置工具白名单

本阶段产出：

- Tool 数据模型
- OpenAPI 导入与解析
- HTTP 工具执行器
- 工具管理页面
- Agent 绑定工具能力

完成标准：

- 用户可以创建或导入工具
- Agent 对话时可以按配置调用工具
- 工具调用失败时有明确错误回传

建议排期：

- 已完成一期基础闭环；后续增强多轮工具调用、工具日志详情和更复杂的 OpenAPI 导入。

### 5.6 发布与集成

对应清单：

- Web UI（对话界面）
- API 接口（供其他内部系统集成）

当前状态：

- 前端已有 `/chat` 对话使用页和 `/conversations` 会话日志页。
- 后端 `conversation` 已有会话 CRUD、消息历史、SSE 流式输出和 Agent 运行预览。
- Web 端基础对话能力已打通。
- 仍缺少正式发布入口和面向外部系统的调用接口。

开发目标：

- 提供 Agent 对话页面
- 提供会话列表、消息流和 SSE 输出
- 提供对外会话 API
- 允许内部系统按 Agent ID 调用

本阶段产出：

- Conversation 数据模型
- 消息存储模型
- SSE 对话接口
- Web 对话页面
- 外部调用 API

完成标准：

- 用户可以在 Web 端与 Agent 连续对话
- 内部系统可以通过 API 发起一次会话调用
- 会话记录可以落库并回看

建议排期：

- `P2` 基础对话能力已完成主体实现
- 下一步进入 `P5` 正式发布与外部集成收口

### 5.7 可观测性

对应清单：

- 对话日志

当前状态：

- 已有基础 observability / metrics / tracing 基础设施。
- 已有会话日志页面。
- 已有工具执行日志和知识库检索日志。
- 尚无串联会话、模型调用、工具调用、RAG 命中的统一运行排查视图。

开发目标：

- 记录会话、消息、模型调用、工具调用、检索命中
- 支持按 Agent、会话、时间范围检索
- 为后续问题排查提供基础证据链

本阶段产出：

- 对话日志模型或聚合查询接口
- 日志列表页
- 关键运行状态透出

完成标准：

- 能定位某个 Agent 的一次执行过程
- 能看见失败发生在模型、工具还是检索阶段

建议排期：

- `P6`

### 5.8 团队管理

对应清单：

- 基础认证（账密）
- 简单权限（管理员 / 普通用户）

当前状态：

- 已有 `users` 表结构和用户管理模块。
- 已有账密登录、JWT access token、`/auth/me` 和前端登录态闭环。
- 当前阶段普通用户和管理员暂时开放同等功能，完整 RBAC 尚未落地。

开发目标：

- 支持登录、登出、鉴权
- 支持管理员 / 普通用户角色区分
- 管理页面默认只允许管理员访问
- 对话使用可向普通成员开放

本阶段产出：

- 登录接口
- JWT 或等价会话机制
- 前端登录页与路由守卫
- 基础角色权限

完成标准：

- 平台有明确的管理员入口
- 非管理员无法修改核心配置

建议排期：

- 已完成基础认证和用户管理；后续 RBAC 可在平台化收口阶段增强。

说明：

如果开发初期需要提速，可以先用单管理员模式推进前几阶段，再补完整认证链路。

### 5.9 部署

对应清单：

- Docker Compose 一键本地部署

当前状态：

- 根文档已把 Docker Compose 作为目标方案
- 当前开发链路仍以本地开发启动为主

开发目标：

- 固化前后端、数据库、Redis、向量能力所需依赖
- 让本地部署过程可重复、可交接

本阶段产出：

- `docker-compose.yml`
- 环境变量模板
- 初始化说明
- 一键启动和验证文档

完成标准：

- 新环境可以按文档直接启动
- 前后端、数据库、缓存和向量检索依赖可以一次拉起

建议排期：

- `P9`

说明：

部署不建议等到最后一天才处理，但“交付级 Compose 收口”放在最后阶段最合理。

## 6. 推荐里程碑

为了便于后续按计划推进，建议用下面三个里程碑管理。

### M1：主链路可用

范围：

- P0 模型管理收尾
- P1 Agent 配置模块
- P2 基础对话运行

结果：

- 已达成：平台可以创建 Agent 并进行基础对话

### M2：Agent 能力完整

范围：

- P3 知识库 / RAG
- P4 工具集成
- P5 发布与集成

结果：

- 部分达成：Agent 已能聊天、查知识、调工具；仍缺少正式发布入口和外部系统调用接口

### M3：平台化收口

范围：

- P6 可观测性
- P7 团队管理
- P8 工作流引擎
- P9 部署

结果：

- 平台具备基本管理能力、可排查能力、复杂编排能力和交付能力

## 7. 下一步建议

如果按本文档推进，下一阶段最合理的开发主题不是继续扩 Provider，而是进入：

`P5：发布与集成模块`

原因：

- 模型、Agent、对话、知识库、工具和登录用户链路已经具备一期基础能力
- 当前平台还停留在“后台管理和 Web 对话可用”，尚未成为可被内部系统稳定调用的应用
- 发布入口和外部 API 是把已有能力产品化的下一步，也是 P6 可观测性与 P8 Workflow 的真实挂载点

建议下一份详细设计文档直接围绕 `publishing/` 或 `app-publishing/` 模块展开，至少补齐：

- 方案设计
- 数据库设计
- 接口设计
- 前端页面设计

重点问题包括：

- Agent 如何发布为独立应用入口。
- 内部系统如何通过 API Key 或等价凭证调用某个 Agent。
- 发布配置如何和草稿 Agent 配置隔离。
- 调用日志、错误、用量如何被 P6 可观测性复用。
