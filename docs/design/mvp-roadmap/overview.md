# Hify MVP 开发计划

## 1. 目标

本文档基于根目录 `CLAUDE.md` 中定义的 MVP 功能清单，结合当前仓库实际进展，整理后续开发计划。

本文档解决三个问题：

- MVP 清单里的每一项，当前做到什么程度
- 后续应该按什么顺序开发，而不是按功能名机械平铺
- 每一阶段完成后，平台能形成什么可验证能力

## 2. 当前状态判断

结合当前代码和设计文档，项目现状可以归纳为：

- 已有前后端基础骨架、统一请求层、主题系统、测试基础设施
- `模型管理` 已经进入一期可用状态，完成了 Provider 聚合 CRUD、密钥加密、前端管理页和一期设计文档
- `agent / conversation / knowledge / tool` 已经有模块骨架和占位接口，但还没有进入真实业务实现
- `auth` 已有用户表基础结构，但登录、鉴权、权限链路还未成型

这意味着后续开发不能平均铺开，而要围绕主链路推进：

`模型管理 -> Agent 配置 -> 对话运行 -> 知识库 / 工具 -> 发布集成 -> 可观测性 -> 团队管理 -> 工作流引擎 -> 部署收口`

## 3. 规划原则

### 3.1 按 MVP 清单管理，按依赖顺序开发

根 `CLAUDE.md` 里的 MVP 清单是产品范围，不是编码顺序。

后续执行时，文档仍按 MVP 清单逐项管理，但实际开发顺序以依赖关系为准。

### 3.2 先打通单 Agent 主链路，再扩展复杂编排

Hify 的核心不是“先做很多配置页”，而是先让用户完成这条链路：

`创建 Agent -> 绑定模型 -> 发起对话 -> 得到稳定回复`

只有这条主链路跑通后，知识库、工具、发布、工作流才有真实挂载点。

### 3.3 Chatbot 模式不单独做一套系统

MVP 中提到 `Agent 模式 + Chatbot 模式`，但落地时不建议做两套并行架构。

更合理的做法是：

- `Agent 模式` 作为完整能力形态
- `Chatbot 模式` 作为受限版 Agent 模板

也就是：

- 固定单模型
- 默认不开工具
- 可选不开知识库
- 仍复用同一套对话与发布链路

这样可以减少后端和前端重复实现。

### 3.4 工作流引擎放到 MVP 后半程

工作流引擎是平台差异化能力，但也是当前清单里实现成本最高、跨模块依赖最多的一项。

如果在 Agent 主链路没有跑通之前就进入工作流开发，后续大概率会反复返工。

因此工作流引擎仍属于 MVP 范围，但排在后半程开发。

## 4. 建议实际开发顺序

建议按下面的阶段推进：

| 阶段 | 对应 MVP 能力 | 目标 |
|---|---|---|
| P0 | 模型管理 | 把当前 Provider 管理模块补到稳定可复用 |
| P1 | 应用编排 | 完成 Agent 配置模块，形成“可保存的 AI 应用” |
| P2 | 应用编排 / 发布与集成 | 打通对话运行时，支持 Web 对话和 SSE |
| P3 | 知识库 / RAG | 让 Agent 能基于私有知识回答 |
| P4 | 工具集成 | 让 Agent 能调用外部 API 做动作 |
| P5 | 发布与集成 | 提供正式应用入口和外部调用接口 |
| P6 | 可观测性 | 形成运行日志、错误追踪和基础分析能力 |
| P7 | 团队管理 | 接入登录、角色和基础权限 |
| P8 | 工作流引擎 | 引入节点编排能力，补齐复杂场景 |
| P9 | 部署 | 完成 Docker Compose 一键交付闭环 |

下面各节仍按根 `CLAUDE.md` 的 MVP 功能清单顺序展开。

## 5. 分项开发计划

### 5.1 应用编排

对应清单：

- Agent 模式
- Chatbot 模式
- 用配置文件 / 表单替代可视化编辑器

当前状态：

- `backend/app/agent/` 只有骨架
- 前端尚无 Agent 管理页
- 对话链路尚未与 Agent 配置打通

开发目标：

- 定义 Agent 作为平台核心应用单元
- 支持创建、编辑、删除、查看 Agent
- 支持绑定默认模型
- 支持配置系统提示词、欢迎语、建议提问
- 支持配置基础对话行为，如是否保留上下文、是否允许工具调用、是否启用知识库
- 以 `app type` 或模板方式兼容 Chatbot 模式

本阶段产出：

- Agent 数据模型与关联关系
- Agent CRUD 接口
- Agent 管理页面
- Agent 配置表单
- Agent 详情 / 测试入口

完成标准：

- 管理员可以创建一个 Agent
- Agent 至少能绑定一个模型
- Agent 配置可以被后续对话模块直接消费

建议排期：

- `P1`

### 5.2 工作流引擎

对应清单：

- LLM 节点
- IF / ELSE 条件分支
- HTTP Request 节点
- 代码执行节点
- Prompt 变量

当前状态：

- 仓库中尚无工作流实体、执行器或前端编排页

开发目标：

- 建立工作流定义模型
- 建立节点执行上下文和变量传递机制
- 支持最小节点集：LLM、条件分支、HTTP 请求、Prompt 变量
- 代码执行节点放在工作流后段实现，避免过早引入沙箱复杂度

本阶段产出：

- Workflow 数据模型
- Workflow 执行引擎
- 最小节点协议
- Workflow 调试 / 运行接口

完成标准：

- 能保存并执行一个最小工作流
- 能在节点间传递上下文和变量
- 能从 Agent 或独立入口触发工作流

建议排期：

- `P8`

说明：

工作流虽然在清单里靠前，但不应先于 Agent 主链路开发。

### 5.3 知识库 / RAG

对应清单：

- 文档上传
- 文本切片
- 向量索引（PGVector）
- 检索测试

当前状态：

- `backend/app/knowledge/` 只有骨架
- 数据模型尚未落地
- 前端无知识库页面

开发目标：

- 支持知识库实体管理
- 支持文档上传、解析、切片、Embedding、入库
- 支持检索测试和命中结果查看
- 支持 Agent 绑定单知识库

本阶段产出：

- `knowledge_bases / knowledge_documents / knowledge_chunks` 等数据结构
- 文档处理任务链路
- 检索接口
- 知识库管理页面
- 检索测试页面或测试弹窗

完成标准：

- 用户可以上传文档并完成索引
- Agent 对话时可基于知识库进行检索增强
- 用户能看到检索是否命中以及命中了什么

建议排期：

- `P3`

### 5.4 模型管理

对应清单：

- 多模型接入（OpenAI + Claude + Gemini + Ollama）
- 模型参数配置

当前状态：

- 已完成 Provider 聚合 CRUD
- 已完成密钥加密与基础模型配置
- 已有前端 Provider 管理页和一期设计文档

待继续内容：

- 健康检查执行接口
- 真正的 LiteLLM 运行时调用打通
- Provider 配置与 Agent 绑定链路联调
- 更完整的错误处理与集成测试

本阶段产出：

- 稳定的 Provider 与 Model 配置来源
- 可被 `agent` 与 `conversation` 复用的模型选择能力
- 健康状态与调用能力校验

完成标准：

- 管理员可以稳定维护 Provider 和模型
- 后续 Agent 配置页可以直接引用模型列表
- 对话运行时可以真实调用已配置模型

建议排期：

- `P0`

### 5.5 工具集成

对应清单：

- 自定义工具
- OpenAPI 导入
- 用户自行接入 API

当前状态：

- `backend/app/tool/` 只有骨架
- 尚无工具实体、执行协议和前端管理页

开发目标：

- 支持工具基本信息管理
- 支持 OpenAPI 导入生成工具定义
- 支持 HTTP 工具执行
- 支持 Agent 配置工具白名单

本阶段产出：

- Tool 数据模型
- OpenAPI 导入与解析
- HTTP 工具执行器
- 工具管理页面
- Agent 绑定工具能力

完成标准：

- 用户可以创建或导入工具
- Agent 对话时可以按配置调用工具
- 工具调用失败时有明确错误回传

建议排期：

- `P4`

### 5.6 发布与集成

对应清单：

- Web UI（对话界面）
- API 接口（供其他内部系统集成）

当前状态：

- 前端已有应用壳，但还没有正式业务对话页
- 后端 `conversation` 只有占位接口

开发目标：

- 提供 Agent 对话页面
- 提供会话列表、消息流和 SSE 输出
- 提供对外会话 API
- 允许内部系统按 Agent ID 调用

本阶段产出：

- Conversation 数据模型
- 消息存储模型
- SSE 对话接口
- Web 对话页面
- 外部调用 API

完成标准：

- 用户可以在 Web 端与 Agent 连续对话
- 内部系统可以通过 API 发起一次会话调用
- 会话记录可以落库并回看

建议排期：

- `P2` 为基础对话能力
- `P5` 为正式发布与外部集成收口

### 5.7 可观测性

对应清单：

- 对话日志

当前状态：

- 已有部分基础 observability / metrics / tracing 基础设施
- 尚无业务级运行日志视图

开发目标：

- 记录会话、消息、模型调用、工具调用、检索命中
- 支持按 Agent、会话、时间范围检索
- 为后续问题排查提供基础证据链

本阶段产出：

- 对话日志模型或聚合查询接口
- 日志列表页
- 关键运行状态透出

完成标准：

- 能定位某个 Agent 的一次执行过程
- 能看见失败发生在模型、工具还是检索阶段

建议排期：

- `P6`

### 5.8 团队管理

对应清单：

- 基础认证（账密）
- 简单权限（管理员 / 普通用户）

当前状态：

- 已有 `users` 表结构
- 尚无完整登录、JWT 和前端鉴权体验

开发目标：

- 支持登录、登出、鉴权
- 支持管理员 / 普通用户角色区分
- 管理页面默认只允许管理员访问
- 对话使用可向普通成员开放

本阶段产出：

- 登录接口
- JWT 或等价会话机制
- 前端登录页与路由守卫
- 基础角色权限

完成标准：

- 平台有明确的管理员入口
- 非管理员无法修改核心配置

建议排期：

- `P7`

说明：

如果开发初期需要提速，可以先用单管理员模式推进前几阶段，再补完整认证链路。

### 5.9 部署

对应清单：

- Docker Compose 一键本地部署

当前状态：

- 根文档已把 Docker Compose 作为目标方案
- 当前开发链路仍以本地开发启动为主

开发目标：

- 固化前后端、数据库、Redis、向量能力所需依赖
- 让本地部署过程可重复、可交接

本阶段产出：

- `docker-compose.yml`
- 环境变量模板
- 初始化说明
- 一键启动和验证文档

完成标准：

- 新环境可以按文档直接启动
- 前后端、数据库、缓存和向量检索依赖可以一次拉起

建议排期：

- `P9`

说明：

部署不建议等到最后一天才处理，但“交付级 Compose 收口”放在最后阶段最合理。

## 6. 推荐里程碑

为了便于后续按计划推进，建议用下面三个里程碑管理。

### M1：主链路可用

范围：

- P0 模型管理收尾
- P1 Agent 配置模块
- P2 基础对话运行

结果：

- 平台可以创建 Agent 并进行基础对话

### M2：Agent 能力完整

范围：

- P3 知识库 / RAG
- P4 工具集成
- P5 发布与集成

结果：

- Agent 不仅能聊天，还能查知识、调工具、被外部系统调用

### M3：平台化收口

范围：

- P6 可观测性
- P7 团队管理
- P8 工作流引擎
- P9 部署

结果：

- 平台具备基本管理能力、可排查能力、复杂编排能力和交付能力

## 7. 下一步建议

如果按本文档推进，下一阶段最合理的开发主题不是继续扩 Provider，而是进入：

`P1：Agent 配置模块`

原因：

- 模型管理已经具备可复用基础
- Agent 是连接配置侧和运行侧的核心实体
- 没有 Agent，后面的对话、知识库、工具都缺少挂载中心

建议下一份详细设计文档直接围绕 `agent/` 模块展开，至少补齐：

- 方案设计
- 数据库设计
- 接口设计
- 前端页面设计

这样后面我们就可以按同样的方式继续推进实现。
