# RBAC 权限管理方案设计

## 1. 背景

Hify 当前已经具备登录、JWT、用户管理和 `admin/member` 两类粗粒度角色，但
权限判断仍主要停留在“是否登录”或少量硬编码管理员判断上。随着 Provider、
Agent、知识库、工具、会话日志和后续发布集成逐步完整，需要一套可维护的 RBAC
权限管理能力来控制不同成员能访问和操作哪些模块。

本模块采用完整 RBAC 表结构，不保留 `users.role` 兼容期。迁移时会将现有
`users.role` 强制映射到内置角色绑定，后续权限解析统一读取 RBAC 绑定关系。

## 2. 一期范围

一期范围：

- 角色管理：列表、详情、新增、编辑、启用、禁用、软删除。
- 权限查看：展示系统内置权限点，支持按模块和动作筛选。
- 角色授权：为角色整体替换权限集合。
- 用户授权：为用户整体替换角色集合。
- 当前用户权限快照：`/auth/me` 和登录响应返回 `roles`、`permissions`。
- 后端权限依赖：新增 `require_permission("permission.code")`。
- 前端权限感知：根据 `permissions` 控制菜单、路由和操作按钮。

一期不做：

- 多租户、组织、部门。
- 字段级权限和数据范围权限。
- 审计日志。
- 权限表达式或策略引擎。
- 页面新增或删除权限 code。
- 外部 SSO/LDAP 权限同步。

## 3. 核心设计原则

### 3.1 权限点系统内置

权限 code 是后端依赖和前端守卫的稳定契约。本期不开放页面创建权限点，避免
管理员创建出代码无法识别的权限。

### 3.2 角色可配置，系统角色受保护

`admin` 和 `member` 是系统角色，不能删除，也不能修改 code。管理员可以创建新的
业务角色，也可以调整角色权限，但任何操作都不能导致系统失去拥有 `rbac.manage`
权限的启用用户。

### 3.3 不保留 `users.role` 双轨

本次不做兼容期。迁移完成后删除 `users.role`，避免出现“用户表角色”和 RBAC
绑定两套权限来源互相打架。

代价是：数据库迁移必须和后端 `auth/user/rbac` 代码改造同一批交付，不能只迁移
数据库后暂停。

### 3.4 前端隐藏不是安全边界

前端可以根据权限隐藏菜单和按钮，但真正的安全边界必须在后端接口依赖中校验。

## 5. 模块边界

`rbac` 模块负责：

- 角色、权限和绑定关系管理。
- 当前用户权限解析。
- 权限依赖函数。

`auth` 模块负责：

- 登录、Token 和当前用户身份识别。
- 调用 RBAC 服务生成权限快照。

`user` 模块负责：

- 账号 CRUD、启用禁用、密码管理。
- 不再直接管理单一角色字段。

业务模块负责：

- 在路由层声明所需权限。
- 不直接读取 RBAC 表做判断。
