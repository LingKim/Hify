# 用户管理方案设计

## 1. 背景

Hify 已有 `users` 基础表。用户管理模块的目标是把内部账号变成可维护的后台资源，为认证、会话归属、Agent/知识库/工具归属以及 RBAC 权限体系提供稳定用户来源。

RBAC 落地后，用户主表不再保存 `role` 字段；用户拥有的角色通过 `user_role_bindings` 维护，权限通过角色绑定的权限点计算。

## 2. 范围

本模块包含：

- 管理员查看用户列表和详情
- 新增用户并设置初始密码
- 编辑用户名、邮箱和启用状态
- 启用或禁用用户
- 重置用户密码
- 软删除用户，并保留历史业务数据归属
- 列表按关键词、角色 ID 和启用状态筛选

本模块不包含：

- SSO、LDAP、OAuth 等外部身份源
- 用户自助注册
- 用户自助修改密码
- 组织、部门、多租户
- 角色创建、权限绑定和用户角色分配页面
- 审计日志
- 复杂企业级密码策略

角色与权限配置归属 RBAC 模块，详见 `docs/design/rbac/`。

## 3. 核心设计原则

### 3.1 认证与账号管理分层

`auth` 模块继续负责登录、Token、当前用户和认证依赖。`user` 模块负责账号 CRUD、启用禁用、重置密码等后台管理能力。

两者复用同一张 `users` 表，但职责不同：

- `auth` 面向“谁正在访问系统”
- `user` 面向“管理员如何维护账号资源”
- `rbac` 面向“用户能访问什么能力”

### 3.2 用户资料不直接承载角色

用户管理接口只维护账号基础资料，不直接读写单一 `role` 字段。

- 新建用户默认绑定内置 `member` 角色。
- 用户列表和详情返回 `roles` 数组，供页面展示。
- 用户角色变更通过 RBAC 用户授权接口完成。

### 3.3 禁用优先于删除

禁用用于停止账号继续访问系统；删除用于管理后台隐藏不再使用的账号。删除必须软删除，避免历史会话、Agent、知识库、工具等记录失去用户归属。

### 3.4 防止系统自锁

用户管理必须避免禁用或删除最后一个拥有 `rbac.manage` 权限的启用用户。该规则替代旧的“至少保留一个 admin 角色用户”规则。

## 4. 推荐方案

采用 `backend/app/user/` 模块实现用户管理：

- 复用 `users` 表作为账号主数据
- 角色和权限统一读取 RBAC 表
- 新增用户管理 API
- 前端沿用 `frontend/src/domain/user-management/` 和 `/users` 页面

这样可以保持账号管理和权限管理边界清晰，避免 `users.role` 与 RBAC 绑定出现双轨冲突。

## 5. 主要用户流程

- 管理员进入用户管理页，查看账号列表。
- 管理员创建用户，填写用户名、邮箱、初始密码和状态。
- 系统自动把新用户绑定到内置 `member` 角色。
- 管理员编辑用户基础资料。
- 管理员禁用用户，用户后续无法登录或继续访问需认证接口。
- 管理员为用户重置密码。
- 管理员软删除用户，历史数据仍保留原用户 ID。
- 管理员如需调整用户角色，进入 RBAC 授权能力完成。

## 6. 验收标准

- 用户列表支持分页、关键词、角色 ID 和状态筛选。
- 可以新增、查看、编辑、软删除用户。
- 可以启用、禁用用户。
- 可以重置密码，接口不返回明文密码或密码哈希。
- 用户名和邮箱在未删除用户中唯一。
- 新建用户默认绑定 `member` 角色。
- 禁用用户无法通过认证访问受保护接口。
- 系统至少保留一个启用且拥有 `rbac.manage` 权限的用户。
- 用户管理接口不再返回或接收 `role` / `roleLabel`。
