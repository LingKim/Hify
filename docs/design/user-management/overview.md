# 用户管理方案设计

## 1. 背景

Hify 当前已经有 `users` 基础表，但会话等功能仍依赖数据库里写死的用户记录。用户管理模块的目标是把内部账号变成可维护的后台资源，为认证、会话归属、Agent/知识库/工具归属以及后续权限体系提供稳定用户来源。

## 2. 一期范围

一期范围：

- 管理员查看用户列表
- 新增用户并设置初始密码
- 编辑用户名、邮箱、角色和启用状态
- 启用或禁用用户
- 重置用户密码
- 软删除用户，并保留历史业务数据归属
- 前端新增“用户管理”页面和导航入口

一期不做：

- SSO、LDAP、OAuth 等外部身份源
- 用户自助注册
- 用户自助修改密码
- 组织、部门、多租户
- 完整 RBAC 权限矩阵管理
- 审计日志
- 复杂企业级密码策略

## 3. 核心设计原则

### 3.1 认证与账号管理分层

`auth` 模块继续负责登录、Token、当前用户和认证依赖。用户管理模块新增为 `user` 业务模块，负责账号 CRUD、启用禁用、重置密码等后台管理能力。

两者复用同一张 `users` 表，但职责不同：

- `auth` 面向“谁正在访问系统”
- `user` 面向“管理员如何维护账号资源”

### 3.2 一期角色简单，后续 RBAC 可扩展

一期只内置两个角色：

- `admin`
- `member`

但数据库预留 RBAC 扩展表设计，后续可以从 `users.role` 平滑迁移到“角色表 + 用户角色绑定 + 权限表”的结构，而不需要重写用户主表。

### 3.3 禁用优先于删除

禁用用于停止账号继续访问系统；删除用于管理后台隐藏不再使用的账号。删除必须软删除，避免历史会话、Agent、知识库、工具等记录失去用户归属。

### 3.4 防止系统自锁

用户管理必须避免删除或禁用最后一个管理员。该规则既是业务规则，也是后续接口实现和测试的必要验收项。

## 4. 推荐方案

采用新增 `backend/app/user/` 模块的方式实现用户管理：

- 复用现有 `users` 表
- 通过 Alembic 迁移补充用户管理字段和索引
- 新增用户管理 API
- 前端新增 `frontend/src/domain/user-management/` 和 `/users` 页面

这样可以保持模块边界清晰，同时避免在 MVP 阶段引入过重的权限系统。

## 5. 主要用户流程

- 管理员进入用户管理页，查看账号列表。
- 管理员创建用户，填写用户名、邮箱、初始密码、角色和状态。
- 管理员编辑用户资料。
- 管理员禁用用户，用户后续无法登录或继续访问需认证接口。
- 管理员为用户重置密码。
- 管理员软删除用户，历史数据仍保留原用户 ID。

## 6. 验收标准

- 用户列表支持分页、关键词、角色和状态筛选。
- 可以新增、查看、编辑、软删除用户。
- 可以启用、禁用用户。
- 可以重置密码，接口不返回明文密码或密码哈希。
- 用户名和邮箱在未删除用户中唯一。
- 禁用用户无法通过认证访问受保护接口。
- 系统至少保留一个启用的管理员账号。
